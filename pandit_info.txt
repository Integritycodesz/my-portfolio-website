## 4. 7 Engineering Masterstrokes (Deep Technical Highlights)
Highlight these specific implementation details in interviews to demonstrate deep software engineering maturity:
### 1. Two-Phase Physical Handshake Protocol (Zero-Fraud Booking Verification)
* 
**
Problem:*
*
 How do you guarantee that a booked priest actually arrived at the devotee's home and conducted the full ritual before disbursing payments?
* 
**
Solution:*
*
  - 
**Phase 1 (Arrival
):*
*
 When the booking is confirmed, a cryptographic 4-digit `
start_otp
` is generated. The Pandit arrives and enters the Start OTP. A `SECURITY DEFINER` RPC `
verify_booking_
otp
(
..., 'start
')`
 verifies the code, transitions state to `
in_progress
`, and immediately invalidates the Start OTP.
  - 
**Phase 2 (Completion
):*
*
 Upon ritual completion, the devotee shares a distinct `
completion_otp
`. Verifying this OTP transitions state to `completed`, automatically triggering double-entry credit into the Pandit's ledger.
  - 
**Zero-Knowledge 
RLS:*
*
 Database RLS explicitly excludes `
start_otp
` and `
completion_otp
` columns from any SELECT query executed by Pandits, preventing client-side inspection or network snooping.
### 2. Double-Entry Financial Ledger with Atomic Balance Invariants
* 
**
Problem:*
*
 Preventing race conditions, duplicate payouts, and floating-point errors in priest earnings and refund processing.
* 
**
Solution:*
*
  - Double-entry ledger table `
pandit_ledger
` where every transaction has a corresponding `
source_type
` (`
booking_earnings
`, `payout`, `
payout_refund
`, `bonus`), `
source_id
`, `amount`, and `
balance_after
`.
  - Stored procedure `process_payout_v2` utilizes `SELECT ... FOR UPDATE` row locks to prevent concurrent double-withdrawal attempts.
  - In the event of a payout rejection by admin or bank gateway, funds are credited back via an atomic ledger reversal with explicit audit notes.
### 3. Split-Payment Engine with Server-Side Cryptographic Signature Verification
* 
**
Problem:*
*
 Ensuring devotees can pay a 20% advance deposit to hold a slot and pay the remaining 80% later, while guaranteeing payment authenticity against client tamper attacks.
* 
**
Solution:*
*
  - Devotee initiates checkout $\
rightarrow
$ Edge Function calculates package costs and creates a 
Razorpay
 Order ID.
  - Client pays $\
rightarrow
$ Devotee App submits `
razorpay_order_id
`, `
razorpay_payment_id
`, and `
razorpay_signature
`.
  - Database RPC `
confirm_booking_payment
` retrieves `RAZORPAY_KEY_SECRET` from secure `
app_secrets
` and verifies the HMAC-SHA256 cryptographic hash (`
extensions.hmac
`).
  - Devotees cannot mutate their own booking status to `confirmed` via SQL—only validated signatures unlock confirmed status.
### 4. Self-Serve B2B Sponsored Ad Monetization Engine
* 
**
Problem:*
*
 Allowing priests to bid on high-intent puja searches with real-time budget depletion and fraud prevention.
* 
**
Solution:*
*
  - Pandits maintain an `
ad_wallets
` balance and configure `
ad_campaigns
` with CPC bids and daily/total budget caps.
  - When devotees search for pujas, the `
search_pujas_and_
pandits
(
)` RPC injects sponsored Pandit profiles at the top based on active campaign bids and relevancy.
  - On click, `
record_ad_
click
(
)` atomically deducts the CPC bid from `
ad_wallets
`, logs the impression/session in `
ad_clicks
`, increments `
amount_spent
`, and automatically pauses the campaign if the balance drops below the CPC threshold.
### 5. Asynchronous Event-Driven Webhook Dispatch via `
pg_net
`
* 
**
Problem:*
*
 Triggering third-party APIs (WhatsApp messages, 
Cashfree
 bank payouts, FCM push notifications) directly from Postgres without blocking ACID transaction threads.
* 
**
Solution:*
*
  - Database triggers utilize the `
net.http
_
post
(
)` asynchronous extension to emit webhook payloads to 
Supabase
 Deno Edge Functions in the background.
  - Edge Functions authenticate with third-party APIs and write results back to `
whatsapp_logs
` and `
payout_requests
`.
  - Database operations complete sub-millisecond, entirely decoupling external API latency from user database writes.
### 6. Event Trigger-Enforced Row-Level Security (`
rls_auto_enable
`)
* 
**
Problem:*
*
 In rapidly evolving schemas, a developer might create a new table and accidentally forget `ALTER TABLE ... ENABLE ROW LEVEL 
SECURITY;`
, creating a catastrophic security loophole.
* 
**
Solution:*
*
  - Implemented a PostgreSQL `EVENT TRIGGER` (`
trg_rls_auto_enable
`) on `
ddl_command_end
`.
  - Any `CREATE TABLE` execution in the `public` schema automatically triggers the event handler to enforce RLS immediately upon creation.
### 7. Dual-Environment Schema Migrator & Persistent Audit Ledger
* 
**
Problem:*
*
 Safely managing database evolution from Development to Production (`with 100% reproducible parity.
* 
**
Solution:*
*
  - Automated diffing script inspects tables, columns, routines, triggers, and secrets across both instances.
  - Implemented an immutable in-database ledger table `_
env_migration_log
` in both environments paired with an in-repo JSON changelog [migration_
history.json
](
file:///e:/drive/broo/.agents/skills/supabase-env-migrator/migration_history.json

## 6. Security & Zero-Trust Architecture
| Security Vector | Implementation Detail | Protection Achieved |
| :--- | :--- | :--- |
| 
**Data Scoping**
 | PostgreSQL Row-Level Security (RLS) on 100% of tables | Clients can only read/write their own records; cross-tenant leaks are mathematically impossible. |
| 
**Privilege Escalation**
 | `SECURITY DEFINER` functions with fixed `
search_path
` (`SET 
search_path
 = public, 
pg_
temp
;`
) | Prevents search-path hijacking attacks in Postgres functions. |
| 
**Sensitive Field Shielding**
 | Explicit column projection & view abstraction | Pandits cannot query OTPs or admin internal review notes. |
| 
**Payment Integrity**
 | Server-side HMAC-SHA256 cryptographic signature validation | Devotees cannot spoof payment completion. |
| 
**Admin Authorization**
 | Subquery check against `
admin_users
` table | Prevents authenticated standard users from accessing admin routes or RPCs. |
